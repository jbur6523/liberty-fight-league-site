# Roll With It – Fan Picks

Public route: `/odds`. This is a free anonymous community poll, with no accounts, wagers, payments, or prizes.

6. Use **Add Image** beside each matched fighter. Accepted uploads are JPEG, PNG or WebP, up to 3 MiB and 24 megapixels. Animated images are rejected. Uploads are decoded, oriented, stripped of metadata, resized without stretching and saved as WebP. Thumbnail, **Replace Image**, and **Remove Image** controls appear after upload.

## Data and voting rules

- Cards read the current event's **active** `superfight_matches`, joined to their actual `fighter_a_id` and `fighter_b_id` competitor records. Bouts with a third or fourth fighter are omitted. No opponents are inferred and no separate fighter list is maintained.
- The existing match trigger makes participants immutable. An opponent change requires unmatching and a new match ID, so old votes cannot follow a fighter into a new pairing. Name, academy and image edits keep votes intact.
- Only competitor ID, first name plus last initial, academy, photo URL, percentages, matchup ID, bout type, agreed weight, real total and the current browser's selected fighter ID leave the public API. Full records, contact fields, cookie identity and IP signals are excluded.
- Each browser receives a random, signed, HttpOnly, SameSite=Lax cookie lasting one year; HTTPS deployments add Secure. Only a keyed hash of its identity is stored with votes. POST requires a valid previously issued cookie. There is no localStorage identity and no Supabase Auth account per visitor.
- `(match_id, voter_hash)` is the database primary key. The service-only voting function atomically upserts the pick, so retries/concurrent submissions and changes count as one vote. Event and match row locks coordinate votes with closing voting, switching the current event and unmatching.
- Persistent database rate limits allow 40 vote submissions per browser per minute, plus 1,200 per network per minute. Shared Wi-Fi visitors get separate votes. IPs are HMAC-hashed, never stored raw; Vercel's trusted IP header is used in production. Expired rate buckets are removed opportunistically after a day. This is abuse resistance for casual polling, not guaranteed person-level uniqueness.
- Percentage A is `round((A + 2) / (A + B + 4) * 100)`, clamped to 1–99; B is its complement. The total is `A + B`. Baselines are never inserted into the vote table.
- Cards refresh after successful votes, when returning to the tab, and every 30 seconds while visible. The public API is uncached. A failed save preserves the last confirmed selection and displays a per-card error.
- Image replacement uses a fresh object path to avoid stale CDN images and compares the previous path before changing the competitor record. A confirmed concurrent loser removes only its newly uploaded object. An uncertain database write retains the new object to avoid breaking a potentially committed reference; an orphan can require later cleanup. Removal clears the competitor reference and removes the old object; already cached copies may remain until their cache expires.

## Verification

Run `npm run check` for module loading, frontend syntax checks and all tests. This static repository has no separate bundler/build command; Vercel serves the static files and packages the `api/` functions. No framework migration was introduced.

Automated checks cover baseline/clamped percentages; signed-cookie validation; the production API against the migration's PostgreSQL functions; concurrent request/retry uniqueness; changed picks; refresh persistence; shared-IP visitors; rate limits; current-event switching; closed voting; removal/rematching and specialty bouts; edits retaining votes; public field filtering; RLS and function grants; storage bucket constraints; photo decoding, upload/replacement/removal and failure cleanup; and admin/cross-origin restrictions. PGlite serializes connections; row-lock behavior on multiple live PostgreSQL connections is not simulated by these tests.

Browser checks used `npm run preview` with explicitly local sample competitors and mock storage/votes. Verified 320px and 390px side-by-side columns without horizontal overflow, equal photo sizes for portrait/landscape uploads, desktop grid, first pick (60–40), changed pick with one total, selection after refresh, image upload/replacement/removal, voting closure, and visible server rejection. Initial public/admin pages had no console errors. Unmatch/rematch and event-isolation behavior are covered by the PostgreSQL/API tests; the browser's native unmatch confirmation blocked automation before that UI check completed.

The visual direction follows the supplied reference: centered two-line title, three short instructions, compact stacked white cards, wide 5:3 photos, a central VS divider, and red/charcoal progress bars and buttons. The header uses the unchanged official RWI SVG and a working site menu. Bout type and agreed weight come from the match record; adult/women's labels are not inferred. Totals exclude baseline votes, as required, even though the reference pictured counts including baselines. The revised layout, navigation, vote update, and refresh persistence were checked again at 320px, 390px and desktop width; all 66 tests passed.

The preview uses sample data only and resets votes/photos when restarted. It is not evidence of a production deployment or live Storage verification.
