# Superfight system technical assessment

## Existing application

- **Framework:** None. The production site is plain HTML and inline CSS served by Vercel.
- **Build/runtime:** There was no `package.json`, build command, test suite, application JavaScript, or server code at the time of the audit.
- **Pages:** `index.html`, `event.html`, `fighters.html`, `contact.html`, `ppv.html`, and the small `crispy.html` redirect document.
- **Fighter application:** `fighters.html` embeds a Google Form. It is independent of the proposed Superfight system.
- **Routing:** Most navigation uses explicit `.html` URLs. `vercel.json` contains ticket/fighter redirects and redirects `/ppv` and `/PPV` to `/ppv.html`.
- **Deployment:** GitHub `main` is connected to the existing Vercel project. The latest audited commit reported a successful Vercel status, and production is served by Vercel. The apex domain redirects to `www.libertyfightleague.com`.

## Existing Supabase and authentication

The repository contains no Supabase client, migrations, project reference, environment variable declarations, authentication flow, admin pages, or authorization conventions. No Supabase CLI or connected Supabase tool was available during the audit, so the external project's current schema and Auth users could not be inspected from this workspace.

The migration in this branch is therefore additive, uses `superfight_`-prefixed objects, and must remain unapplied until the existing project's schema has been reviewed. It does not create a Supabase project.

## Existing brand assets

- `rwi-logo.svg`: canonical Liberty Fight League/RWI logo per repository guidance; new Superfight pages use it without modification.
- `logo.png`: legacy raster logo still used by parts of the existing site.
- `poster.jpg`: current event poster.
- `ppv-splash.png`: PPV artwork.
- The live site already links to `https://instagram.com/libertyfightleague`.
- The current visual system is dark with gold, restrained red/blue accents, and bold condensed/display typography. The Superfight public experience can simplify this to the requested black-and-white presentation while retaining the logo and typography cues.

## Production risks and constraints

1. Replatforming the entire site before building the feature would put every current page and redirect at risk without providing immediate product value.
2. Clean URLs such as `/event` and `/fighters` currently return 404; existing pages link to `.html` paths. New routes need explicit Vercel rewrites rather than assuming framework routing.
3. `vercel.json` contains two `/nico` redirect entries and three placeholder fight destinations. They are pre-existing and are intentionally left unchanged.
4. Existing HTML contains copy, markup, and apparent character-encoding issues. They are outside this feature and should not be mixed into Superfight implementation commits.
5. A Supabase service-role key must only be supplied to Vercel server functions. It must never be included in public JavaScript.
6. No event details or weight classes should be seeded until they are provided by the promoter.

## Recommended architecture

Keep the existing static site and redirects intact. Add narrowly scoped static pages for the fighter and promoter interfaces, plus Vercel serverless endpoints that access the existing Supabase project. This avoids a whole-site framework migration and keeps the current deployment model.

Public browser code should never query private tables directly. Server endpoints should expose only the fields required by each page. Promoter sign-in should reuse Supabase Auth, with membership in `superfight_admin_users` determining access. This is an authorization layer on the existing Auth system, not a second authentication system.

Secure status and confirmation tokens are UUIDv4 values generated by PostgreSQL. RLS is enabled on every new table, anonymous table access is revoked, and public requests must pass through server endpoints. Confirmation responses are retained as part of match history. Unmatching changes the match state and does not delete competitors or confirmations.

## Proposed data model

- `superfight_events`: event identity, date/time, venue, public application copy, application-open state, and configurable LFL Instagram URL.
- `superfight_event_weight_options`: event-specific display labels with canonical numeric pounds for sorting and compatibility scoring.
- `superfight_competitors`: public applications and admin quick-add records, private contact details, normalized Instagram fields, secure status token, notes, and simple merge lineage.
- `superfight_matches`: promoter-approved fighter pairs, match weight, active/unmatched state, and audit fields.
- `superfight_match_confirmations`: one secure link and response per fighter per match.
- `superfight_admin_users`: Supabase Auth users allowed to use promoter tools.

## Proposed route structure

Public pages:

- `/superfight` — current/selected event landing page and one-question application.
- `/status/:token` — privacy-filtered fighter status.
- `/confirm/:token` — match confirmation and gym-only edit.

Promoter pages:

- `/admin/superfights` — event selector and summary.
- `/admin/superfights/unmatched` — suggested matchmaking workspace and quick add.
- `/admin/superfights/matched` — matchup/confirmation workspace.
- `/admin/superfights/competitors/:id` — full private competitor detail.

Server APIs will mirror these capabilities under `/api/superfight` and `/api/admin/superfight`, with public and promoter response shapes kept separate.

## Implementation sequence

1. **Foundation:** reviewable SQL migration, token/security model, normalization and deterministic matchmaking utilities, and tests.
2. **Connection/API:** inspect and link the existing Supabase project; add server-only clients, public submission/status/confirmation APIs, promoter session enforcement, and API tests.
3. **Public UI:** event landing page and animated mobile application, then status and confirmation pages.
4. **Promoter UI:** unmatched workspace, manual match creation, matched workspace, competitor detail, and quick add.
5. **Integration hardening:** Vercel rewrites, mobile/desktop visual QA, accessibility, production-like build checks, and documented migration rollout.
6. **Controlled rollout:** apply the reviewed migration to the existing Supabase project, configure the existing Vercel project, create/authorize promoter users, seed a real event and real weight options, then deploy through the existing repo/project only.
